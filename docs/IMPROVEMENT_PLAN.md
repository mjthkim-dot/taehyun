## 1. 설계 원칙 (4개 → 재정의)

### 원칙 1. 런타임에 생성하지 않는다. 조회한다. — **유지, 목적 재정의**

원안은 이 원칙의 근거를 "지연 제거"로 뒀다. **지연은 이미 해결됐다**
(EN 완결 1.49초). 이 원칙의 진짜 값은 다른 데 있다.

> 목적은 **재현성과 환각 차단**이다. 같은 질문에 같은 답이 나와야 리허설이
> 의미를 갖고, 대본에 없는 문장이 화면에 뜨지 않아야 발화가 안전하다.

### 원칙 2. **답변의 부가 줄을 핫패스에서 뺀다** — 범위 축소

원안 "런타임 번역 홉 0"은 성립하지 않는다. 면접관 발화는 예측 불가라
**자막 번역은 제거 대상이 아니다**(그게 이 도구의 핵심 기능이다).

| 번역 홉 | 제거 | 이유 |
|---|---|---|
| 자막 한국어 번역 | ✗ | 면접관 발화는 사전 컴파일 불가 |
| 답변의 KR 줄 | ✓ | 내 답변이므로 사전 컴파일 가능 |
| 답변의 PR 줄(한글 발음) | ✓ | 동상 |

→ 회수 가능한 시간은 **1.51초**(측정치). 자막 경로는 건드리지 않는다.

### 원칙 3. **세션은 크기가 아니라 의미를 기억한다** — 교체

원안의 "컨텍스트 예산 고정"은 이미 3중으로 지켜지고 있다(§7-2). 대신 진짜
빠진 것은 이것이다.

> 지금 시스템은 "**무엇을 이미 말했는지**"를 모른다. 같은 딜 스토리를 두 번
> 꺼내도 막지 못하고, 앞서 말한 수치와 뒤 수치가 어긋나도 알지 못한다.

### 원칙 4. 근거가 없으면 출력하지 않는다 — **유지, 1순위 승격**

현재 코드는 정반대를 지시한다.

> `prompts.py:188` — `NEVER dodge: no "I'm not sure"... always give a
> speakable, confident answer grounded in the profile.`

검색이 컷을 통과하지 못해도 프로필로 답을 만든다. **미스가 그럴듯한 답에
덮여 보이지 않는다.** 16개 구성요소 중 유일한 D등급이다.

### 원칙 5 (신규). **입력이 깨지면 라우팅도 깨진다**

원안은 입력 품질을 다루지 않는다. 그러나 8/27 실전의 오답은 라우팅 실패가
아니라 **STT 파손**에서 왔다("Workato"→"avocado"). 결정론적 문자열 매칭은
정확할 때 강하지만 **깨진 입력에는 임베딩보다 취약하다.**

> 그러므로 라우팅은 "결정론 우선, 임베딩 폴백"이 아니라 **"결정론과 임베딩을
> 함께 채점하고, 둘 다 낮으면 미스로 떨어뜨린다"**여야 한다.

## 2. 목표 아키텍처

### 2-1. 답변 유닛 — **신규 작성이 아니라 승격**

원안은 40~60개를 새로 쓰는 것으로 잡았다. 실측하면 **이미 절반이 존재한다.**

| 현황 | 수치 |
|---|---|
| 개인 노트 청크 | 72건 |
| `[검색어]` 트리거를 이미 보유 | **66건 (92%)** |
| 트리거가 **영어**(면접관 표현) | **57건** |
| 본문이 거의 영어(즉시 발화 가능) | 34건 |

원안 스키마와 현재 청크의 차이는 **필드 4개뿐**이다.

| 원안 필드 | 현재 상태 |
|---|---|
| `id` | ✓ 청크 id 존재 |
| `trigger_phrases` | ✓ `[검색어]` 줄 (57건 영어) |
| `answer_en_30s` | △ 34건만 영어 완성형 — **나머지 보강 필요** |
| `answer_en_90s` | ✗ 신규 |
| `intent_tags` | ✗ 신규 |
| `key_numbers` | ✗ 신규 (수치 게이트용) |
| `conflicts_with` | ✗ 신규 (중복 방지용) |
| `source_file` | ✓ title로 대체 가능 |

→ 작업은 "60개 작문"이 아니라 **"기존 청크에 필드 4개 얹기 + 30초/90초 판본
정리"**다. 대상도 전체가 아니라 **면접 응답용 상위 30~40건**이면 충분하다.

### 2-2. 3티어 런타임 — 목표치를 실측 기준으로 재설정

| 티어 | 동작 | 원안 목표 | **수정 목표** | 근거 |
|---|---|---|---|---|
| A 인텐트 히트 | 유닛 그대로 표시, LLM 없음 | 500ms | **150ms 이내** | 검색 자체가 1.1ms |
| B 부분 히트 | 유닛 조합·미세조정, 스트리밍 | 첫 토큰 1.5s | **첫 토큰 0.9s 유지** | 현재 TTFT 0.82s |
| C 미스 | **생성하지 않음** | — | 확정 사실+키워드만 | 신규 |

원안의 "Tier A로 70~80% 처리" 목표는 **측정 후에 정한다.** 근거 없이 못
박으면 A티어를 억지로 늘려 엉뚱한 대본을 띄우게 된다. 골든셋(§5-1) 1회
실행 후 실측값으로 확정한다.

### 2-3. 세션 의미 상태

크기 관리는 불필요(이미 고정). 다음만 유지한다.

- `used_unit_ids` — 같은 딜 스토리 반복 차단(`conflicts_with`와 대조)
- `stated_numbers` — 이미 발화한 수치와 표현 형태
- `interview_stage` — 도입 / 경력검증 / 시나리오 / 역질문
- `open_threads` — 물었으나 답 못 준 항목

## 4. 개인화 — 원안 유지 (근거 보강)

원안의 "런타임 프롬프트로 풀지 말고 사전 컴파일에 박아라"는 옳다. 근거를
덧붙이면, 현재 프롬프트 8,300자 중 **75%가 지시문**이고 말투 규칙도 그 안에
있다. 유닛에 박으면 지시문이 줄어 프롬프트도 가벼워진다.

원안의 문장 기준(단문·15단어·숫자로 마감·낭독처럼 들리지 않기)은 그대로 쓴다.
다만 **끊어 읽기 슬래시(`/`)는 이미 구현돼 있다** — 유닛에도 같은 표기를 넣어야
표시 계층과 어긋나지 않는다.

## 6. 착수 전 확인 3가지 (원안 5개에서 축소)

1. **다음 면접 대상 회사.** 현재 코퍼스는 Workato 중심에 GitLab 피치가 얹혀
   있다. 유닛 승격 대상 30~40건의 선정이 여기에 달렸다.
2. **면접 중 KR·PR을 실제로 보는가.** Phase 1의 -1.5초는 이 둘을 뒤로
   미루는 대가다. 안 본다면 끄는 것이 가장 빠르고 안전하다(호출 수도 안 는다).
3. **Tier C에서 무엇을 보고 싶은가.** "대본 없음"만? 확정 수치+키워드까지?
   시간 벌기 문장("Let me think about that for a second")까지?

L1~L4 16개 구성요소의 정확한 정의는 §7-5의 내 매핑으로 갈음한다 — 다르면
알려주면 그 축으로 다시 매핑한다.

## 8. 가장 먼저 고칠 단 하나

**Phase 0의 미스 처리** — 사전 컴파일보다 앞선다.

1. **위험이 가장 크다.** 화면 문장은 그대로 발화된다. 지연은 어색함을 낳지만
   환각은 **거짓 경력 진술**을 낳는다. 되돌릴 수 없다.
2. **가장 싸다.** 유닛 승격은 2~3일이지만 이건 분기 하나와 프롬프트 한 줄이다.
3. **나머지의 전제다.** 미스를 기록해야 무엇을 컴파일할지 알 수 있다.
4. 실측상 10문항 중 1건이 이미 컷 탈락 후 프로필로 답하고 있었고, 사용자는
   그것이 대본 기반인지 구분할 수 없었다.
