# 실시간 영어 미팅 어시스턴트 — 아키텍처

> 한국인 IT 영업 실무자를 위한 **실시간 영어 미팅 보조 + 개인화 RAG**.
> Smooth AI(smoothai_kr)의 UX를 기준선으로 삼되, 차별점은 하나다:
> **사용자의 학습 이력과 업무 도메인을 검색해, 그 사람이 실제로 말할 법한 문장을 만든다.**
>
> 코드 위치: `meeting-copilot/` · 계획과 수용 기준: [PLAN.md](./PLAN.md)

## 0. 이 문서가 전제하는 사용자 환경

설계 판단의 근거이므로 먼저 못박는다. (앞선 프로젝트에서 실측·확인된 사실)

| 제약 | 실측/근거 | 설계에 미치는 영향 |
|---|---|---|
| 회사망이 일부 LLM 도메인 차단 | `api.groq.com` 403 (키 재발급해도 동일), 반면 구글 도메인은 통과 | 단일 공급자 의존 금지, 네트워크 의존 최소화 |
| 맥북 16GB | Apple Silicon, Ollama 설치됨 | 로컬 임베딩 가능, 단 8B 초과 모델은 회의 중 부담 |
| 비용 $0 우선 | 사용자 요구 | 유료 벡터DB·임베딩 API 배제 |
| 개인용 단일 사용자 | 동시 접속 1명 | 대규모 인프라 불필요, 브루트포스 검색으로 충분 |
| 미팅 트랜스크립트는 민감 | 고객사명·계약 규모 포함 | 외부 전송 최소화가 기본값 |

## 1. 전체 구조

```
┌─ 브라우저 (PWA, 미팅 중 사이드 패널) ──────────────────┐
│  STT: Web Speech API(P0) / 탭 오디오 캡처(P1)          │
│  자막 → 한국어 번역 → 발언 제안 카드                    │
└───────────────┬───────────────────────────────────────┘
                │ 같은 출처 HTTP (CORS 미개방)
┌───────────────▼───────────────────────────────────────┐
│  로컬 서버 (Python stdlib, 맥북에서 실행)               │
│   ├ RAG: SQLite 벡터 스토어 + 하이브리드 검색           │
│   ├ 임베딩: Ollama bge-m3 (로컬·$0·한↔영)              │
│   └ LLM: Groq → Cerebras → Gemini → Ollama 자동 전환   │
└───────────────┬───────────────────────────────────────┘
                │ 인제스트 (미팅 전, 오프라인)
      ┌─────────┴──────────┬──────────────────┐
   Notion 수업노트    미팅 트랜스크립트     도메인 용어집
```

## 2. 프론트엔드 — 미팅 중 사이드 패널

미팅 화면이 주인공이고 이 앱은 곁눈질 대상이다. 그래서 전체화면 앱이 아니라
**좁고 세로로 긴 컴팩트 레이아웃**을 기본으로 한다.

- **폭 360~420px 기준 설계** — 맥 화면 우측에 Zoom/Meet과 나란히 두는 용도.
  브라우저 창을 좁히면 자동으로 이 모드가 된다(컨테이너 쿼리 아님, 뷰포트 폭 기준).
- **PWA** — `manifest` + 서비스워커. 홈 화면/독에 설치해 앱처럼 띄운다.
  오프라인 캐싱은 셸(HTML/CSS/JS)만. 대화 데이터는 캐싱하지 않는다.
- **시선 이동 최소화**: 제안 문장은 카드 최상단, 굵게, 글자 크기 3단계 조절.
  마우스 조작은 미팅 화면에 드러나므로 키보드 단축키를 1급으로 취급한다.
- **읽는 중 보호**: 새 발언이 들어와도 고정(pin)된 카드는 덮어쓰지 않는다.

> 근거: 앞선 `interview-coach`에서 동일 패턴을 구현·검증했다(단축키 9종 테스트 통과,
> 모바일 뷰포트 9종 통과). 그 UI 결정을 그대로 계승한다.

## 3. STT (음성 인식)

| 단계 | 방식 | 이유 | 한계 |
|---|---|---|---|
| **P0** | Web Speech API | 유일한 **무료 실시간 스트리밍** 인식. 키 불필요, 한도 없음 | 시스템 기본 입력만 들음 · iOS Safari 불안정 |
| **P1** | `getDisplayMedia({audio:true})` 탭 오디오 캡처 | 브라우저 탭(Zoom Web/Meet)의 소리를 **직접** 캡처 → 오디오 라우팅 설정 불필요 | 크롬 계열 전용 · 네이티브 앱 소리는 못 잡음 |
| 보조 | Whisper 배치 (로컬 faster-whisper / Groq) | 정확도 우선 구간, 사후 아카이빙용 | 실시간 아님(문장 단위 지연) |

**구현 시 확인된 제약**: `SpeechRecognition`은 **MediaStream을 입력으로 받지 못한다**
(시스템 기본 입력만 듣는다). 따라서 탭 오디오는 Web Speech에 넣을 수 없고,
VAD로 문장 단위로 잘라 서버 Whisper로 인식해야 한다.
→ 대가: **interim 자막이 사라진다**(말하는 중 미리보기·투기적 선생성 불가).
→ 이득: 오디오 라우팅 설정이 0이고, 디지털 신호라 잡음이 없어 인식률이 오른다.
두 방식을 헤더에서 고르게 두고 기본은 실시간(Web Speech)으로 둔다.

**P1이 P0보다 중요한 이유**: Web Speech는 시스템 입력만 듣기 때문에 BlackHole 같은
가상 오디오 장치 설정이 필요하다. `getDisplayMedia`는 탭을 공유하는 순간 그 탭의
오디오가 바로 들어오므로 **설정이 0**이다. 다만 화면 공유 권한 UI가 뜨고 크롬 전용이라
P0에서는 검증된 Web Speech로 먼저 동작시키고, P1에서 캡처 경로를 추가한다.

**실시간성 설계**: Web Speech는 말이 끝난 뒤에도 1~2초 지나야 문장을 확정(`isFinal`)한다.
그 시간을 버리지 않기 위해 **중간 결과가 안정되면 미리 생성을 시작**한다(투기적 선생성).
확정 문장이 미리 쓴 문장을 92% 이상 포함하면 그대로 채택하고, 아니면 재생성한다.
→ 앞선 프로젝트 실측: 발화 종료 후 답변 표시 **1.81초 → 0.57초**.

## 4. RAG 레이어 — 선택지 비교와 결정

### 4.1 후보 비교

| 항목 | A. transformers.js (브라우저) | B. 서버리스 + 관리형 벡터DB | **C. SQLite + 로컬 임베딩** |
|---|---|---|---|
| 비용 | $0 | 무료 티어 有, 볼륨 늘면 과금 | **$0** |
| 한↔영 교차검색 | 다국어 모델 필요 → 용량 급증 (multilingual-e5-small ~120MB, bge-m3 ~2GB) | 모델 선택 자유 | **bge-m3 로컬 (~1GB, 1회 받음)** |
| 최초 실행 | 모델 다운로드 20~2000MB | 즉시 | Ollama pull 1회 |
| 아카이브 색인 속도 | WASM 느림 (수십 chunk/s), 메인스레드 잼 | 빠름 | **빠름 (네이티브)** |
| 기기 간 동기화 | IndexedDB에 갇힘, 기기마다 재색인 | 자동 | 서버 1대가 진실 |
| 네트워크 의존 | 없음(캐시 후) | **있음 — 이 사용자에겐 실증된 실패 요인** | 없음 |
| 프라이버시 | 최상 (기기 밖으로 안 나감) | 트랜스크립트가 외부로 나감 | **상 (맥북 안)** |
| 메타데이터 필터 | 직접 구현 | SQL/필터 지원 | **SQL 그대로** |

### 4.2 결정: **C — SQLite 벡터 스토어 + Ollama bge-m3 임베딩**

**채택 근거**
1. **네트워크 의존이 이 사용자에게 실증된 실패 요인이다.** 회사망이 `api.groq.com`을
   차단해 서비스가 통째로 멈춘 사례가 있다. 미팅 도중 검색이 막히면 앱의 존재 이유가 사라진다.
2. **한↔영 교차 검색이 요구사항의 핵심이다.** 수업 노트는 한국어, 미팅은 영어다.
   브라우저에서 이걸 하려면 다국어 모델이 필요한데 용량이 감당 안 된다.
   Ollama `bge-m3`는 이미 앞 프로젝트에서 동작을 확인했다.
3. **개인용 규모에서 ANN이 불필요하다.** 청크 2만 개 기준 브루트포스 코사인이
   파이썬에서 수십 ms다. 인덱스 자료구조를 도입할 이유가 없다.
4. **트랜스크립트는 맥북 밖으로 나가지 않는 게 기본값이어야 한다.**

**의존성을 어떻게 0에 가깝게 유지하나**
- 저장: 파이썬 표준 라이브러리 `sqlite3` (설치 불필요). 벡터는 `BLOB`(float32 배열)로 저장.
- 검색: 순수 파이썬 브루트포스 코사인. numpy도 선택 사항으로 둔다(있으면 빠르게, 없으면 그대로 동작).
- 가속(선택): `sqlite-vec`가 설치돼 있으면 ANN 인덱스를 쓴다. **없어도 기능은 동일**하다.

**저하 사다리 (degradation ladder)** — 아무것도 없어도 죽지 않게
```
bge-m3 있음   → 하이브리드(키워드 + 벡터, RRF 융합)   ← 최상
Ollama 없음   → 키워드 전용 (BM25 유사 점수)          ← 여전히 유용
색인 없음     → 원문 전체 주입 (소량일 때만)           ← 최소 동작
```
> 근거: 앞 프로젝트에서 "인덱스가 없으면 영어 질문이 한국어 문서와 전혀 매칭되지 않아
> 10개 질문이 전부 같은 문서로 떨어지는" 결함을 겪었다. 그래서 **키워드 경로가 단독으로도
> 쓸 만해야 한다**를 설계 원칙으로 승격한다 (문서에 영문 키워드를 함께 심는 방식).

### 4.3 검색 파이프라인

```
발언(영어) ─┬─→ 키워드 점수 (BM25 유사, 불용어 제거)  ─┐
            └─→ 임베딩 → 코사인 top-k                 ─┴─→ RRF 융합 → top-6
                                                            ↓
                          소스 다양성 보정(한 소스가 독점 못하게) → 프롬프트 주입
```
- **RRF(Reciprocal Rank Fusion)**를 쓰는 이유: 두 점수의 스케일이 달라 가중합은 튜닝이 필요하지만,
  RRF는 순위만 쓰므로 스케일 프리다.
- **소스 다양성**: 용어집만 6개 뽑히면 문맥이 빈다. 소스당 최대 3개로 제한한다.
- **근거 표시**: 어떤 청크에서 나온 제안인지 카드 하단에 노출한다(사용자가 사실 여부를 확인 가능).

## 5. 데이터 소스 3종

| 소스 | 내용 | 청킹 단위 | 인제스트 경로 | 쓰이는 곳 |
|---|---|---|---|---|
| **Notion 수업 노트** | 영어 수업에서 배운 표현·교정받은 문장·발음 지적 | 노트 블록/문단 | 내보내기(md/csv) 붙여넣기 → P2에서 API 동기화 | "내가 배운 표현으로" 제안 생성 |
| **미팅 트랜스크립트 아카이브** | 지난 미팅의 내 발화 + 상대 발화 | 발화 묶음(주제 단위) | 세션 종료 시 자동 적재 | 반복 상황 재사용, 내 말투 학습 |
| **도메인 용어집 (클라우드 세일즈)** | AWS/Azure/GCP·FinOps·보안·계약 용어의 한↔영 대응과 실제 문장 | 용어 1개 = 1청크 | 시드 JSON + 트랜스크립트에서 자동 추출 | 정확한 용어 선택, 오역 방지 |

**왜 이 3종인가**: 제안 문장의 품질은 세 가지가 동시에 맞아야 자연스럽다 —
**말투**(내가 실제로 쓰는 표현 = 수업 노트·트랜스크립트),
**용어**(그 업계에서 통하는 단어 = 용어집),
**맥락**(지금 이 미팅에서 무슨 얘기 중인가 = 실시간 자막).
하나라도 빠지면 "번역기 같은 문장" 또는 "내가 못 쓰는 문장"이 나온다.

**자기 강화 루프**: 미팅이 끝날 때마다 트랜스크립트가 아카이브로 들어가고,
새 용어가 용어집으로 승격된다. 쓸수록 개인화가 깊어진다.

## 6. LLM 계층

`Claude(Anthropic) → Cerebras → Groq → Gemini → Ollama` 순서로 시도하고, 401/403/404/429·연결 실패 시
해당 공급자를 60초 제외하고 다음으로 넘어간다. 스트리밍은 첫 청크를 확인한 뒤 커밋하므로
헤더 전송 후 실패로 새지 않는다.

**Claude를 1순위로 두는 이유**: 이 앱의 체감 품질은 곧 *구어체 한국어 자막*의 품질이다.
번역투("~하는 것으로 사료됩니다")는 읽는 데 시간이 더 걸려서 실시간 자막으로는 실패다.

**모델을 두 개로 나눈다** — 경로마다 요구가 다르기 때문이다.

| 경로 | 모델 | 이유 |
|---|---|---|
| 자막 번역 · 한 줄 요약 | `ANTHROPIC_FAST_MODEL` (기본 Haiku 4.5) | 초당 수십 번 도는 실시간 경로. 지연이 곧 품질 |
| 발언 제안 | `ANTHROPIC_MODEL` (기본 Sonnet 5) | 내 자료를 읽고 문장을 만드는 추론 — 품질 우선 |

`llm.stream_ndjson(..., fast=True)`로 경로를 구분한다. 다른 공급자로 넘어가면
그 공급자의 기본 모델을 쓴다.

실측(발화 종료 → 제안 표시): Cerebras 0.55s · Groq 0.67s · Gemini Flash 1.34s · Ollama 8B 1.98s.

### 실시간 호출 규율 (번역·요약)

미팅 1시간이면 발화가 수백 건이다. 호출을 그대로 흘리면 한도와 지연이 동시에 무너진다.

- **번역**: 레인 2개 병렬. 같은 문장은 **API를 한 번만** 부르고 결과를 캐시해
  재사용한다. 중복 제거를 *표시*에까지 적용하면 되묻기·재확인처럼 같은 말이
  실제로 두 번 나올 때 두 번째 자막이 빈 채로 남는다(실제로 겪고 고침).
  진행 중인 요청에는 합류시킨다.
- **롤링 요약**: 최근 **10발화** 버퍼, **3문장 누적 또는 30초 경과** 시 갱신.
  호출은 항상 1개만 떠 있게 하고(single-flight), 진행 중에 조건이 또 걸리면
  쌓지 않고 표시만 남겼다가 끝난 뒤 **1회만** 재실행한다(coalescing).
  버퍼 내용이 직전 요약과 동일하면 호출 자체를 건너뛴다.

## 7. 보안 · 프라이버시

- **CORS 미개방** — 프런트가 같은 출처이므로 CORS가 불필요하다. 와일드카드를 열면
  사용자가 방문한 임의 사이트가 트랜스크립트를 읽고 사용자 키로 API를 호출할 수 있다.
  (앞 프로젝트에서 실제로 뚫려 있던 것을 확인하고 막았다.)
- **기본 바인딩 127.0.0.1** — LAN 노출은 명시적 옵션.
- **공개 배포 시 접속 코드 필수** — 지수 백오프 잠금 + 상수 시간 비교,
  쿠키에는 코드 원문 대신 HMAC 유도 토큰.
- **트랜스크립트는 로컬 SQLite에만** 저장하고 `.gitignore`로 커밋을 차단한다.

## 8. `interview-coach`와의 관계

같은 저장소의 `interview-coach/`는 **면접**용(1:1 Q&A, 사전 답변셋)이고,
이 앱은 **실무 미팅**용(다자·연속 대화·도메인 용어·후속 액션)이다. 목적이 달라 별도 앱으로 둔다.

다만 검증된 부품은 재사용한다 — 재작성하면 이미 잡은 결함을 다시 만들 뿐이다.

| 재사용 | 왜 |
|---|---|
| 다중 공급자 LLM 전환 (`llm.py`) | 회사망 차단 대응이 이미 검증됨 |
| 투기적 선생성 로직 | 지연 68% 단축이 실측됨 |
| 보안 설정 (CORS·접속코드·백로그 128) | 실제 취약점을 찾아 고친 결과 |
| 컴팩트 UI·단축키 패턴 | 테스트 통과한 상호작용 |

**재사용하지 않는 것**: 질문 은행, 사전 답변셋, STAR 피드백 — 면접 전용 개념이다.


## 7. 웹 서비스 계층 (배포 모드)

로컬 개인 앱과 웹 서비스는 **같은 코드, 다른 설정**이다. 상세 절차는 [DEPLOY.md](./DEPLOY.md).

```
브라우저 ──HTTPS/H2── Caddy (TLS·타임아웃·압축) ──HTTP/1.1 keep-alive── server.py (127.0.0.1)
                                                                    ├─ auth.py    세션·쿼터
                                                                    ├─ rag.Store  사용자별 SQLite
                                                                    └─ llm.py     공급자 체인
```

핵심 결정과 근거:

| 결정 | 근거 |
|---|---|
| 사용자 1명 = SQLite 파일 1개 (`u/<id>/store.db`) | 격리가 물리적 — 쿼리 실수로 남의 데이터가 섞일 수 없다. 검색 직렬화 락이 사용자별로 쪼개진다. 백업·탈퇴가 파일 단위 |
| 인증은 "사용자 존재"로 자동 활성 + 무인증 외부 바인딩은 기동 거부 | "일단 0.0.0.0으로 열어보자"가 사고가 되지 않게 (fail-safe) |
| 세션 = HMAC 서명 토큰 (서버 무상태) | 재시작해도 로그인 유지, 세션 테이블 불필요 |
| 사용자별 LLM 쿼터 (15회/분 · 600회/일) | 서버의 API 키가 곧 지갑 — 실측 미팅 소비 3.8회/분의 4배 여유로 정상 사용은 걸리지 않는다 |
| HTTP/1.1 keep-alive + 청크 스트리밍 | 웹에서는 호출마다 TCP/TLS 핸드셰이크(+60~150ms)가 실시간 경로에 직결 — QA 실측 후 전환 |
| 소켓 타임아웃 30초 · 본문 상한 8MB | slowloris·대용량 선언 공격을 QA에서 실측, 차단 |
| 표준 라이브러리 유지 (FastAPI 이관 안 함) | 병목은 서버가 아니라 LLM 쿼터·STT CPU (실측). 의존성 0 원칙. 웹 방어는 Caddy가 담당 |
